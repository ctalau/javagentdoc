2.1 CODE REVIEW - SemanticXmlDoclet.java

   POSITIVE FINDINGS:
   ✓ Correct Doclet interface implementation
   ✓ Proper use of DocletEnvironment and DocTrees APIs
   ✓ Option parsing implemented correctly
   ✓ XML generation using StAX (no external dependencies)
   ✓ Both XML and Markdown output paths implemented
   ✓ Handles packages, classes, methods, fields, constructors
   ✓ Error handling with try/catch and reporter
   ✓ Uses Files API for safe file I/O
   ✓ Creates output directories if missing (line 136)

   ISSUES IDENTIFIED:

   Issue #1: Incomplete Semantic Structure (CRITICAL)
   Location: Lines 357, 366
   Problem: Uses dt.toString() and tag.toString() instead of proper DocTree visitor
   Impact: Block tags (@param, @return, @throws, etc.) are converted to strings
           but not parsed into semantic elements
   Expected: Should have a DocTreeVisitor to extract tag names, values separately
   Result: Output loses semantic relationship between tag names and descriptions

   Issue #2: Potential NPE in Directory Creation
   Location: Line 136
   Problem: Files.createDirectories(outFile.toAbsolutePath().getParent());
           - If outFile is a path without parent directory, getParent() can return null
   Impact: Would crash when generating to file in current directory
   Expected: Should check if parent is null before calling createDirectories

   Issue #3: Markdown Doc Comment Conversion
   Location: Lines 246, 281, 300, 320-321
   Problem: Uses doc.toString() which just converts the entire comment tree to string
   Impact: @param, @return, @throws tags are appended as raw text, not parsed
   Expected: Should extract individual tags and format them semantically
   Result: Markdown output loses semantic structure

   Issue #4: Missing Inline Tag Support
   Location: Throughout documentation extraction
   Problem: {@link}, {@code}, {@literal}, {@value} tags not handled as semantic elements
   Impact: Inline tags appear as raw text in output
   Expected: Should convert to structured elements or proper Markdown formatting

   Issue #5: No Generic Type Parameter Support
   Location: Line 271, 308, 342
   Problem: Using asType().toString() for type info, not capturing generics properly
   Impact: Generic type information may not be fully preserved
   Expected: Should use full qualified type with generic parameters

   Issue #6: Class Kind Name Formatting Bug
   Location: Lines 240-242
   Problem: Using kind.substring() could fail on short strings, and capitalization is manual
   Impact: Markdown headers might have inconsistent formatting
   Expected: Should use proper enum value names or constants
